## 一、数据库变更（prisma schema）

### 1.1 Task 模型变更

```prisma
model Task {
  id               String    @id @default(uuid())
  userId           String
  parentId         String?
  title            String
  description      String?

  taskType         String    @default("inbox")   // 保留字段名，语义=「计划状态」inbox/planned/scheduled
  status           String    @default("not_started")

  // ❌ 删除：startTime / endTime（时间只走 Schedule）
  deadline         DateTime?

  importance       Int       @default(3)
  // ❌ 删除：temperature

  estimatedMinutes Int?
  actualMinutes    Int       @default(0)

  tags             String?   // 仅存用户自由标签（迁移脚本剥离 domain:/theme:/important: 前缀）
  snoozeUntil      DateTime?

  sortOrder        Int       @default(0)
  completedAt      DateTime?
  createdAt        DateTime  @default(now())
  updatedAt        DateTime  @updatedAt

  category         String?   // 领域：course|learning|practice|health|life|external|other（移除 competition）
  theme            String?   // ✅ 新增：主题（自由文本单选，如 "考研" / "竞赛"），✅ 已确认加索引

  // AI 增强（planner 消费，保留 4 个）
  complexity       String?
  riskLevel        String?
  dependencies     String?
  scheduleAdvice   String?
  // ❌ 删除：cognitiveLoad / schedulingHint（phase 级 ParsedPhase 已有，Task 级冗余）

  phaseOrder       Int       @default(0)

  postponedCount   Int       @default(0)
  source           String    @default("user")
  level            String?   @default("task")
  accumulate       Boolean   @default(false)

  // ...relations/index 不变；✅ 新增 @@index([userId, theme])（已确认）
}
```

### 1.2 数据迁移（一次性脚本）

| 步骤 | 操作 |
|------|------|
| 1 | `prisma migrate dev` 应用字段变更（删 temperature/startTime/endTime/cognitiveLoad/schedulingHint，加 theme） |
| 2 | 回填 theme：`category = 'competition'` 的行 → `category = 'practice'` + `theme = '竞赛'` |
| 3 | 回填 theme：标题含「考研/数学/英语/政治/专业课」关键词的 learning 任务 → `theme = '考研'`（保留学习领域，如用户可再改） |
| 4 | 清理 tags：剥离 `domain:*` / `theme:*` / `important:*` 前缀，仅保留自由标签 |
| 5 | 校验：无 competition 残留、无 domain: 前缀、无死字段写入 |

### 1.3 其他表

- `Schedule`：不动（唯一时间源已确立）
- `TimeLog`：不动（type 含 focus/checkin）
- `TaskExecutionFeedback` / `AgentFeedback`：不动（字段已够，见 §5 链路扩展）

## 三、API 层变更

### 3.1 新增接口

| 方法 | 路由 | 用途 | 契约要点 |
|------|------|------|---------|
| `GET` | `/api/tasks/search?q=` | 全局搜索 | 标题 contains + tags contains + 归属链 title；返回 `{ results: [{ id, title, category, theme, status, parentTitle, scheduledStart? }] }`；复用 resolver/`@@index([userId,title])`；空 q 返回 400 |

### 3.2 修改接口

| 路由 | 改动 |
|------|------|
| `POST /api/tasks` | body 加 `theme?`；移除 temperature/startTime/endTime 支持（scheduled 自动建 Schedule 不变）；category 白名单 7 类 |
| `PUT /api/tasks/[id]` | 白名单加 `theme`（单一入口：身份层在档案面板/Inbox 可改）；移除 temperature/startTime/endTime 写入 |
| `POST /api/inbox/analyze` | 响应 `items[]` 加 `theme`（AI 推断 + 规则降级） |
| `GET /api/views/today` | `currentTask` 加 `theme/themeColor`；Focus Card 增加主题小徽章数据 |
| `GET /api/views/week-calendar` | `scheduledTasks/plannedTasks` 加 `theme`；图例返回 `themes: [{name,color}]`（当前周出现的主题） |
| `GET /api/tasks/[id]` | **档案面板聚合扩展**：+`theme`、+`ancestors`（归属链数组）、+`schedules`（全部排期）、+`accumStats`、+`aiFields`（complexity/riskLevel/dependencies/scheduleAdvice 只读） |
| `GET /api/views/stats` | 分类统计自然收敛为 7 类；tagBreakdown 不再需要过滤 domain:/theme: 前缀（数据已清）；✅ 本期实施 `?theme=` 过滤 + themeBreakdown（主题投入分析，见 §6.3） |

### 3.3 删除/停用路由（工程师确认零引用后删）

| 路由 | 理由 |
|------|------|
| `POST /api/ai/ingest` | 被 agent/chat + inbox/analyze 替代 |
| `POST /api/ai/today-suggest` | 被 views/today + today-decide 替代 |
| `POST /api/plan/edit-schedule` | 被 schedule PUT + shiftSchedules 替代 |
| `POST /api/plan/delete-schedule` | 被 schedule DELETE + deleteFutureSchedules 替代 |
| `GET /api/views/week` | 被 week-calendar 替代（历史遗留） |
| **保留** `/api/plan/repeat` | 积累型重复排期仍依赖（V5 已接线） |

## 四、AI 链路与反馈通道

### 4.1 数据库 → AI 链路新增

| 链路 | 新增内容 |
|------|---------|
| buildAgentContext | 注入 theme 分布：「用户当前主题 X/Y，各 N 个任务」→ LLM 建议更贴合目标 |
| pattern-mining | ✅ 新增 Rule10「主题时段偏好」：theme 聚合任务的时间分布 → UserPattern（如「考研任务集中在晚上」）；可选增强，不阻塞主链路 |
| planner | theme 上下文注入（§2.5） |
| today-decide | analysis 追加主题信息（可选） |

### 4.2 反馈通道新增（Inbox 确认的修改要回流）

```
现状：Inbox 确认时用户改 category/theme → 目前无反馈采集（仅忽略/采纳有）
✅ 新增：确认时检测「AI 推断值 ≠ 用户最终值」：
  category 修改 → AgentFeedback(userResponse='modify', modifiedField='category', originalValue, userValue, taskId)
  theme 修改   → AgentFeedback(..., modifiedField='theme', ...)
消费：
  computeTrustScore 计入（用户常改 → AI 信任下降）
  memory-learning 可挖掘「领域/主题修正模式」（如：AI 总把考研任务判成 learning，用户改实践 → 学规则）
```

### 4.3 AI 增强字段使用边界（文档化红线）

```
complexity/riskLevel/dependencies/scheduleAdvice：
  仅 planner 与 AI 建议消费；任何 UI 组件禁止直接展示（档案面板 AI 区块折叠只读除外）
```

## 六、产品定位与逻辑问题（独立审查）

> 用户要求：除信息混用外，审查产品定位/产品逻辑层面的问题。

### 6.1 产品定位：个人成长系统，不是通用效率工具

- 现状证据：领域 7 类中 5 个学业相关（课程/学习/实践/竞赛/外部），用户行为数据以考研/电赛/毕设为主——**产品是「学生/备考生的成长系统」，不是泛用 GTD**
- 影响：7 类封顶的领域边界与人生阶段绑定；若未来进入职场场景，需重新评估领域集（新增「工作」或重构）
- 建议：定位写进 README/总控文档，所有功能决策对照「是否服务成长闭环」（输入→规划→执行→复盘）

### 6.2 北极星指标缺失（产品无量化目标）

- 现状：功能丰富但没有任何「成功指标」仪表
- 建议（配合路线图 §指标设计）：
  - 北极星：周任务完成率（含打卡率加权）
  - 驱动：今日路线采纳率 / Inbox 确认率 / 7 天打卡保持率
  - 健康：任务堆积率（>7 天未处理 = 过滤失败信号）、周回归率
  - 反指标：AI 建议修改率（用户常改 = 规则引擎该调）
- 落地：Review 页面增加「指标卡」区块（数据全来自 stats API，零新后端）

### 6.3 「主题」上线后 Review 的高价值升级点

- 主题 = 目标 = 最有复盘价值的维度：**「考研投入 X 小时，占本周 60%，连续 3 周上升」**比「学习成长 30 小时」更有行动意义
- ✅ **已确认本期实施**：stats API 增加 themeBreakdown（按 theme 聚合时长/完成数）+ Review 战报「主题投入」区块（主题名 + 时长 + 占比 + 周环比）；数据源为 Task.theme 聚合，无 AI 依赖

### 6.4 提醒与「过滤未来」的张力（红线）

- 打卡提醒/截止提醒是「推」信息，与「用户主动打开」理念相悖
- 红线：提醒只服务**承诺兑现**（积累型打卡、截止日前 1 天），且必须可一键关闭；禁止泛通知（新功能、周报推送等）
- 判断工具：信息展示四关（Q1 能改变行为吗 / Q2 此刻需要吗 / Q3 重复吗 / Q4 有行动指向吗）

### 6.5 数据主权与可迁移性

- 导出 JSON 已有，但无 schema 版本号——主题/分类升级后旧导出无法映射
- 建议：导出文件加 `schemaVersion` 字段 + 迁移映射表；长期评估 CSV/周报 PDF 导出（路线图 Later）

### 6.6 单任务卡片的信息层级（一致性红线）

- 所有卡片（Today/Plan/Project/收集箱/搜索结果）统一：**身份 → 时间 → 状态** 三层，其余进详情
- 形态推断规则文档化（有排期→计时 / 有子任务→清单 / accumulate→积累 / 否则→学习），禁止任何页面自创卡片样式

### 6.7 AI 透明化的产品边界

- Settings 的 AI 记忆仪表盘是差异化点（AI 透明），但主流程只展示**结论和建议动作**，不展示推理过程
- 红线：Trust Score / 记忆列表 / 决策日志只出现在 Settings；主流程 AI 输出遵循「结论 + 可应用动作」格式（Review「下周可以试试」是范本）
