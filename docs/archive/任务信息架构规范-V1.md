# Task OS 任务信息架构规范 V1

> 版本：V1.0（待审核） | 日期：2026-08-02  
> 状态：**产品规划稿，未实施** | 配套文档：任务层级重构-V5定稿.md、UI数据源与脱节分析.md  
> V1 目标：回答「一个任务的信息谁填、在哪填、在哪显示」，为后端架构与前端 UI 提供统一基准。

---

## 一、背景与目标

Task OS 的任务身上有 20+ 个信息字段，散落在 5 个页面。现状问题：

1. **定位不清**：每个信息维度没有明确「管理页面」，Plan/Project/Inbox 的编辑能力边界模糊
2. **维度混用**：分类体系把「领域」与「目标/状态」混在一个维度（竞赛冲刺是目标态却成了领域类；「考研」被硬塞进 learning）
3. **概念命名冲突**：taskType（inbox/planned/scheduled）与卡片形态（计时/清单/积累）都叫「类型」，用户无法区分

本规范确立三件事：

- **五层信息模型**：每个信息字段归一层，每层只有一个管理页面
- **四维分类模型**：形态 / 领域 / 主题 / 项目 各管各的，互不混淆
- **架构与 UI 落地指引**：后端数据规则 + 前端展示规则

## 二、五层信息模型

> 核心原则：**一个信息只有一个「家」，在哪生，就在哪管。**

### 2.1 总览

| 层      | 回答的问题     | 管理页面    | 谁来填              | 可否编辑      |
| ------ | --------- | ------- | ---------------- | --------- |
| 身份层    | 它是谁       | Inbox   | AI 解析 + 人工确认     | 创建时定，可改   |
| 结构层    | 它属于哪、包含啥  | Project | 人工（拖拽/键盘）        | 随时改，AI 不碰 |
| 时间层    | 它什么时候做    | Plan    | 人工（拖拽/详情），AI 只建议 | 随时改，必须确认  |
| 执行层    | 它做得怎么样    | Today   | 执行时自动产生          | 执行时操作     |
| AI 增强层 | AI 怎么辅助排期 | 无（全自动）  | AI               | 只读，不进卡片   |

### 2.2 身份层（Inbox 定）

| 字段               | 含义                            | 谁来填              | 显示位置         |
| ---------------- | ----------------------------- | ---------------- | ------------ |
| title            | 标题                            | AI 提取 + 确认       | 所有卡片         |
| category         | 领域（四维分类）                      | AI 推断 + **人工确认** | 周历底色/卡片徽章    |
| theme（新）         | 主题（四维分类）                      | AI 推断 + 人工确认     | 周历角标/详情      |
| taskType         | 计划状态（inbox/planned/scheduled） | AI 判断 + 确认       | 收集箱/详情       |
| estimatedMinutes | 预估时长                          | AI 估算 + 确认       | 时间块          |
| source           | 来源（user/ai）                   | 系统打标             | 收集箱「AI 解析」徽章 |

**规则**：身份层是**全系统唯一的人工确认点**（Inbox 确认表单）。确认后进入各层。

### 2.3 结构层（Project 管）

| 字段          | 含义                     | 管理方式         |
| ----------- | ---------------------- | ------------ |
| parentId    | 归属（项目树）                | 拖拽/键盘流/菜单    |
| level       | 层级（project/phase/task） | 节点菜单标 ★      |
| accumulate  | 积累型开关                  | 节点菜单         |
| children    | 执行清单                   | 行内勾选/追加/拖拽排序 |
| description | 备注                     | 详情面板编辑       |
| sortOrder   | 同级排序                   | ↑↓ 按钮        |

**规则**：结构层**唯一入口是 Project 页**，AI 永不直接改（AI 解析建树需在 Inbox 确认时预览）。

### 2.4 时间层（Plan 管）

| 字段                          | 含义    | 管理方式                   |
| --------------------------- | ----- | ---------------------- |
| Schedule.scheduledStart/End | 排期时间块 | 周历拖拽/详情调整              |
| deadline                    | 截止日   | 详情面板                   |
| 续排                          | 明天继续  | continue_tomorrow / 拖拽 |
| estimatedMinutes 修正         | 时长修正  | 详情面板                   |

**规则**：**Schedule 是唯一时间数据源**（核心规则，已确立）。Task.startTime/endTime 是死字段，见 §6 问题 P1-3。

### 2.5 执行层（Today 产生）

| 字段           | 含义      | 产生方式        |
| ------------ | ------- | ----------- |
| status       | 状态      | 开始/完成/跳过/暂停 |
| TimeLog      | 计时/打卡记录 | 计时器自动写入     |
| children 勾选态 | 执行清单进度  | 勾选自动完成      |
| completedAt  | 完成时间    | 完成动作写入      |

**规则**：执行层数据由 Today 页操作产生，其余页面只读。

### 2.6 AI 增强层（全自动）

| 字段                             | 含义        | 用途      |
| ------------------------------ | --------- | ------- |
| complexity                     | 复杂度       | AI 排期建议 |
| riskLevel                      | 风险等级      | AI 排期建议 |
| dependencies                   | 依赖关系      | AI 排期建议 |
| scheduleAdvice                 | 排期建议      | AI 建议展示 |
| cognitiveLoad / schedulingHint | 认知负荷/排期提示 | AI 建议展示 |
| postponedCount                 | 推迟次数      | 行为统计    |

**规则**：**不进任何任务卡片**，只进 AI 建议/Review 归因。用户可关 AI 后完全忽略。

### 2.7 单一编辑入口原则（收银台模式）

- **读聚合**：任何页面点任务 → 打开「任务档案面板」（见 §5.2），五层信息全部可见
- **写分散**：档案面板中每层信息的编辑仍走对应页面逻辑（身份→Inbox 表单、结构→Project、时间→Plan），不新增平行编辑入口
- **反例禁止**：不允许出现两个页面都能改同一字段（如 Plan 详情和档案面板同时改 deadline）

## 三、四维分类模型

> 核心原则：**四个维度各管各的，永不合并，永不互相替换。**



| 维度    | 回答       | 数量        | 谁定               | 决定什么    |
| ----- | -------- | --------- | ---------------- | ------- |
| 形态    | 怎么显示     | 固定 4 种    | AI 推断 + Inbox 确认 | 卡片长相与操作 |
| 领域    | 属于什么生活内容 | **7 类封顶** | Inbox 确认         | 颜色基调    |
| 主题（新） | 为了什么目标   | 自由扩展      | 标签，随手打           | 角标色     |
| 项目    | 在哪棵树     | 任意深度      | Project 页        | 归属链     |

### 3.1 形态（卡片形态，不落库、前端推断）

| 形态  | 判定规则              | 例子     | 卡片特征          |
| --- | ----------------- | ------ | ------------- |
| 计时型 | 有排期、无子任务、非积累      | 上课/开会  | 计时圆环          |
| 清单型 | 有子任务（children 非空） | 画原理图   | 执行清单勾选        |
| 学习型 | 无排期、无子任务、非积累      | 精读论文   | 进度 + 勾选       |
| 积累型 | accumulate=true   | 背单词/健身 | 打卡 + 连续天数/周视图 |

> 说明：形态由数据推导（schedule / children / accumulate），**不落库**是设计决策，避免多字段互相矛盾。

### 3.2 领域（7 类封顶，不再增加）

| key      | 中文      | 底色 border | 浅底 bg   |
| -------- | ------- | --------- | ------- |
| course   | 课程      | #475569   | #E2E8F0 |
| learning | 学习成长    | #2563EB   | #EFF6FF |
| practice | 专业实践    | #7C3AED   | #F5F3FF |
| health   | 健康生活    | #16A34A   | #F0FDF4 |
| life     | 个人事务    | #CA8A04   | #FEFCE8 |
| external | 社团/外部   | #F97316   | #FFF7ED |
| other    | 未分类（兜底） | #CBD5E1   | #F8FAFC |

**为什么 7 类封顶**：人眼在周历上可快速区分的颜色上限为 5-7 个，超过即糊。新增的「目标类」诉求一律走主题（§3.3），不碰领域。

### 3.3 主题（新机制，自由扩展）

- **定义**：任务服务的大目标（考研/竞赛/毕设/求职/考公…）
- **存储**：复用 tags 前缀机制——`theme:考研`、`theme:竞赛`（与现有 `domain:xxx` 同构，零 schema 改动）
- **默认配色（暂定，待 UI 设计师确认）**：

| 主题 | 角标色       | 备注                 |
| -- | --------- | ------------------ |
| 竞赛 | 红 #DB2777 | 沿用现有 competition 色 |
| 考研 | 橙 #F97316 | 待 UI 设计师调          |

- **显示**：Plan 周历任务块 = 领域底色 + 主题角标；Today/Project 卡片 = 主题小徽章
- **解析**：AI parser 增加 theme 推断（可选），Inbox 确认表单可编辑
- **竞赛冲刺的处理**：竞赛任务 = 领域 practice + 主题竞赛（红角标）。现有 competition 类**一期兼容保留**，二期可收敛（见 §6 P0-1）

### 3.4 项目（Project 树）

- 任意深度树（项目 → 阶段 → ★任务 → 执行项），parentId 自关联
- 由 Project 页树形大纲管理，归属链在 Today/档案面板显示
- **考研落位示例**：考研（项目）→ 数学/英语（阶段）→ 「考研数学第三章」（★任务）→ 执行项

### 3.5 四维决策速查

```
「考研数学」  = 形态:清单型 + 领域:学习(蓝) + 主题:考研(橙角标) + 项目:考研›数学
「电赛调试」  = 形态:计时型 + 领域:实践(紫) + 主题:竞赛(红角标) + 项目:电赛
「背单词」    = 形态:积累·每日 + 领域:学习(蓝) + 主题:考研(橙) + 项目:考研›英语
```

## 四、后端架构设计

### 4.1 数据模型现状与建议

| 现状字段                                                                               | 归属层     | 建议                               |
| ---------------------------------------------------------------------------------- | ------- | -------------------------------- |
| Task.category                                                                      | 身份      | 保留，**字段为准**，normalizeCategory 兜底 |
| Task.tags                                                                          | 身份/主题   | 规范前缀体系（见 4.2）                    |
| Task.taskType                                                                      | 身份      | 保留（inbox/planned/scheduled）      |
| Task.level / accumulate                                                            | 结构      | 保留                               |
| Task.description                                                                   | 结构      | 保留                               |
| Task.importance                                                                    | 身份（隐藏）  | 与 temperature 二选一（见 §6 P1-2）     |
| Task.temperature                                                                   | 身份（隐藏）  | 见 §6 P1-2                        |
| Task.startTime/endTime                                                             | **死字段** | 只读兼容，禁止新写入；时间一律走 Schedule        |
| Task.complexity/riskLevel/dependencies/scheduleAdvice/cognitiveLoad/schedulingHint | AI 增强   | 保留，标注「AI 内部字段，UI 不展示」            |
| Schedule.scheduledStart/End                                                        | 时间      | 唯一时间源                            |
| TimeLog                                                                            | 执行      | 含 checkin 类型（打卡）                 |

**零 schema 改动优先**：theme 用 tags 前缀，不新增列。仅当 V2 确认 importance/temperature 合并等决策时再动 schema。

### 4.2 tags 前缀规范

```
domain:xxx    领域（唯一事实源冗余到标签，供 resolveDomain 兜底）
theme:xxx     主题（新）
important:xxx 重要标记（系统）
其余          用户自由标签
```

- 解析顺序：`domain:` 标签 → `theme:` 标签 → 标题关键词推断
- Review 关键词统计须过滤 `domain:/theme:/important:` 系统前缀（现状已过滤 domain/important，需补 theme）

### 4.3 API 设计（新增/调整）

| API                          | 用途              | 状态                                |
| ---------------------------- | --------------- | --------------------------------- |
| `GET /api/tasks/search?q=`   | 全局搜索（标题/标签/归属链） | 新增                                |
| `GET /api/tasks/[id]`        | 档案面板数据（五层聚合）    | 扩展：补 theme/ancestors/schedules 聚合 |
| `POST /api/tasks/[id]/theme` | 打/改主题标签         | 新增                                |
| Inbox analyze/confirm        | theme 推断 + 确认   | 扩展                                |
| week-calendar                | 返回 theme + 主题色  | 扩展                                |

### 4.4 数据规则（红线）

1. **Schedule 唯一时间源**：任何时间修改必须经 Schedule Service（$transaction）
2. **单一编辑入口**：同一字段禁止两个页面可写
3. **分类字段为准**：Task.category 是事实源，tags 的 domain: 为冗余，resolveDomain 仅兜底推断
4. **形态不落库**：卡片形态由数据推导，禁止新增 type 字段造成双轨
5. **AI 不直接写结构/时间**：AI 建树/排期必须经用户确认（Inbox 表单 / apply-decision）

## 五、前端 UI 设计

### 5.1 卡片三层显示规则

任何任务卡片（Today/Plan/Project/收集箱）**只显示三层**：

1. **身份**：标题 + 形态徽章 + 领域色
2. **时间**：排期时间块或截止日（红/琥珀梯度）
3. **状态**：进度/打卡/完成

其余（备注、清单、归属链、AI 字段）一律收进详情。**卡片是提示牌，详情才是档案室**——与「过滤未来」理念一致。

### 5.2 任务档案面板（核心新组件）

- **打开方式**：任意页面点击任务卡片 / 搜索结果 → 弹出档案面板
- **形态**：宽面板（≈560px），五层分区块：身份 / 结构 / 时间 / 执行 / AI（折叠）
- **编辑跳转**（收银台模式）：
  - 身份 → 面板内编辑（Inbox 确认逻辑）
  - 结构 → 「去 Project」（跳转定位树节点）
  - 时间 → 「去 Plan」（跳转定位时间块）
  - 执行/AI → 只读
- **基础**：现有 TaskDetailPopover 升级（已有点击弹出 + 三类型主视觉 + 子任务操作）
- **工作量**：1-2 天

### 5.3 全局搜索

- 顶部导航搜索框：输入关键词 → 结果列表（标题/标签/归属链匹配）→ 点击打开档案面板
- 后端复用 resolver 关键词搜索（已建 `@@index([userId, title])`）
- **工作量**：0.5-1 天

### 5.4 Plan 周历主题角标

- 任务块 = 领域底色（现有）+ 左上角主题角标（竞赛红/考研橙）
- 图例区补主题说明
- **工作量**：0.5 天

### 5.5 Inbox 确认表单增强

- 确认表单增加：主题输入（chips 预设：考研/竞赛/毕设 + 自定义）、形态预览（推断结果展示）
- AI 解析结果展示 theme 推断值，人工可改

## 六、审查发现：现有维度混用问题清单

> 本次审查结论。**V1 先记录，修订进 V2**。

### P0（用户已感知，必修）

| #    | 问题                        | 证据                                      | 建议                                              |
| ---- | ------------------------- | --------------------------------------- | ----------------------------------------------- |
| P0-1 | competition 是「目标态」却混入领域维度 | DOMAINS 8 类含 competition；用户感知「实践升级竞赛变红」 | 主题机制承接；competition 一期兼容、二期收敛为 practice+theme:竞赛 |

### P1（命名/概念冲突，应在 V2 明确）

| #    | 问题                                                     | 证据                                              | 建议                                              |
| ---- | ------------------------------------------------------ | ----------------------------------------------- | ----------------------------------------------- |
| P1-1 | taskType（inbox/planned/scheduled）与卡片形态（计时/清单/积累）都叫「类型」 | parser prompt「判断任务类型」=taskType；用户口述「积累型/时间型」=形态 | 规范命名：taskType 改称「计划状态」，形态称「卡片形态」；UI 文案区分        |
| P1-2 | importance(1-5) 与 temperature(4 档) 表达同一概念              | importanceToTemperature 纯映射                     | V2 决策：二选一（建议保留 importance，temperature 移除或改派生展示） |
| P1-3 | Task.startTime/endTime 死字段 vs Schedule 唯一时间源           | 日志已确认死字段                                        | 禁止新写入；parser 输出不再落 Task 时间；V2 可考虑 db 迁移删除       |
| P1-4 | tags 维度混杂                                              | CSV 混 domain:/important:/普通标签                   | 前缀规范（§4.2）；Review 过滤补 theme                     |

### P2（语义重叠/边界模糊，V2 观察）

| #    | 问题                                                                | 建议                                                      |
| ---- | ----------------------------------------------------------------- | ------------------------------------------------------- |
| P2-1 | complexity/riskLevel/cognitiveLoad 三个三值字段语义部分重叠                   | 标注 AI 内部字段；V2 评估收敛为 1-2 个                               |
| P2-2 | level=task 的执行项与独立任务无法区分                                          | 约定：有 parentId 且父为 ★task 的 task 节点 = 执行项（文档化，不落库）        |

| P2-4 | status 的 snoozed 与 delayed 语义重叠                                   | V2 评估状态机简化                                              |
| P2-5 | category 三轨存储（字段/domain 标签/推断）                                    | 明确「字段为准、标签冗余、推断兜底」（已写入 §4.4）                            |
