**审查人**：Senior Developer（高级开发工程师）

**审查范围**：src/ 全量（55 页面 + 40 API 路由 + AI 决策引擎 + Schedule Service）

## 一、总体结论

项目架构思路清晰（Schedule 唯一时间源、零 AI 可用的规则引擎、四页面闭环），这个设计骨架是好的。但**工程质量处于"原型可用、生产脆弱"阶段**，存在 3 个 P0 级系统性问题：

1. **时区处理系统性错误**（25+ 处 `toISOString().split("T")[0]`）——每天 20:00 后全项目"今天"变"昨天"
2. **大量假交互按钮**——看起来能点、点了没反应，直接摧毁用户体验
3. **分类枚举双轨制**（COURSE vs course）——同字段存两套值，UI 分类丢失

另有 P1 级问题 15 项（事务缺失、权限矩阵倒挂、状态机缺陷等），详见下文。

**好消息**：核心规则引擎（today-decide / pattern-mining）逻辑本身是自洽的，Schedule Service 的事务模型（moveSchedule 的 verify 模式）方向正确——只是执行不彻底。

## 二、P0 — 必须立即修复（按优先级排序）

### P0-1 时区系统性错误：`toISOString().split("T")[0]` 取"本地日期" ❗最严重

**位置**：25+ 处，包括：
- `src/lib/ai/parser.ts:319,348` — fallback 解析器相对日期（明天/后天/本周X）
- `src/lib/ai/parser.ts:93,246` — 给 LLM 的"今天日期"（prompt 注入）
- `src/lib/ai/client.ts:18-29` — Agent 系统提示词中的今天/明天/本周五/下周一
- `src/lib/ai/daily-summary.ts:75,89` — 每日摘要日期键
- `src/app/api/views/today/route.ts:21` — Today 页 dailyBrief 查询键
- `src/app/api/ai/today-decide/route.ts:25` — TodayDecision 查询键
- `src/lib/ai/today-decision.ts:75,94`、`src/lib/task/task-execution-state.ts:65`、`src/app/api/daily-note/route.ts:33-34` 等

**根因**：`toISOString()` 返回 **UTC** 时间。在中国（UTC+8），每天 **20:00–24:00**（UTC 已跨天）时：
- 本地 8/2 20:30 → `toISOString()` = `2026-08-02T12:30Z` → `split("T")[0]` = `"2026-08-02"` ✅ 正常
- 本地 8/2 21:30 → `toISOString()` = `2026-08-02T13:30Z` → 仍为 8/2 ✅
- 本地 8/3 00:30 → UTC 8/2 16:30 → 得 `"2026-08-02"` ❌ **晚于 0 点的"今天"是昨天**

**实际影响**：
1. 晚上 8 点后（UTC 已跨天时）Today 页面显示**昨天的完成数**、dailyBrief 查**昨天的简报**
2. LLM 拿到的"今天"是错的 → **AI 推算的"明天/后天/下周三"全部错一天**
3. fallback parser 的"明天 3 点"→ startTime 错一天；且 `toISOString().replace("Z","")` 截断还把本地 15:00 存成 07:00（**偏移 8 小时**）
4. 晚睡用户（项目目标人群！）在晚间使用率最高，**命中概率极高**

**修复方案**：新建 `src/lib/date.ts` 统一出口：

```ts
// 本地时区日期字符串（YYYY-MM-DD），禁止再用 toISOString().split("T")[0]
export function localDateStr(d: Date = new Date()): string {
  const y = d.getFullYear(), m = d.getMonth() + 1, day = d.getDate();
  return `${y}-${String(m).padStart(2, "0")}-${String(day).padStart(2, "0")}`;
}
export function localDateTimeStr(d: Date): string { /* 同理本地时区 YYYY-MM-DDTHH:mm:ss */ }
```

全项目替换，并在 `tests/date.test.ts` 写时区回归测试（mock 系统时区为 UTC+8 断言 0 点边界）。

### P0-2 假交互：大量按钮无事件绑定（三处页面）

| 页面 | 假按钮 | 后果 |
|---|---|---|
| **Today** | FocusCard 的「完成」「跳过」、右上角「更多」、「调整」状态、「采纳」建议 | 核心操作全部不可用，产品无法使用 |
| **Inbox** | SimpleCard/ComplexCard 的「编辑」、「+ 添加阶段」、底部「撤销」 | 用户改完发现不生效 |
| **Plan** | 「展开时间轴」、收集箱任务 `cursor-grab`（无拖拽实现）、周历任务块 `cursor-pointer`（无点击） | 规划页不可操作 |

**ComplexCard 编辑是"假编辑"**（`page.tsx:151,156`）：`defaultValue` 非受控 + slider 显示固定 `t.estimatedMinutes`，用户改了也不提交 → **数据不随 UI 变化**。

**修复方案**：
- Today：「完成」→ POST `/api/tasks/[id]/action`（complete）；「跳过」→ postpone/reschedule；「采纳」→ apply-decision
- Inbox：编辑改为受控组件，把编辑结果并入 confirmOne 提交体
- 要么实现，要么移除（临时方案：隐藏按钮，避免"可点假象"）

### P0-3 分类枚举双轨制：COURSE vs course

**位置**：
- LLM prompt + fallback parser → 大写 `COURSE/LEARNING/PRACTICE/...`（`parser.ts`）
- `TaskForm` + `lib/plan/colors.ts` DOMAINS → 小写 `course/learning/practice/...`
- 两套值混存于同一 `Task.category` 字段，`POST /api/tasks` 不校验

**后果**：TaskForm 手动创建的任务在 Plan 周历上**永远显示"未分类"**（`TaskCategoryEnum["course"]` = undefined → fallback UNCATEGORIZED）；pattern-mining 的 category 统计也失真。

**修复方案**：统一为一种（建议统一为小写 DOMAINS key），改造点：
1. `parser.ts` CATEGORY_RULES 返回值 + LLM prompt 枚举 → 小写
2. `types/task.ts` TaskCategoryEnum 加小写兼容映射（迁移期）
3. `POST /api/tasks` 用 zod 校验 category 值域

## 三、P1 — 重要问题（建议 1-2 周内修完）

### P1-1 Schedule 创建非事务
`schedule/service.ts` 的 `createSchedule` / `createScheduleWithSource`：先 `deleteMany` 再 `create`，**两步无事务**（`moveSchedule` 有事务，风格不一致）。中间崩溃 → 任务没有 schedule 且旧 schedule 已删。应统一为 `$transaction`。

### P1-2 权限矩阵倒挂（违反产品原则）
`tools.ts` 中：
- `create_task`（最无害，新建）→ **confirm** 需要确认
- `update_task` / `schedule_task`（修改现有任务、**覆盖已有排期**）→ **write 直接执行**

AI 一句话"把实验报告改到周五"就能直接覆盖用户排期，**无需任何确认**。与"用户最终控制权，AI 只建议不强制"的核心原则直接冲突。建议 `schedule_task` 升为 confirm；或至少对覆盖已有 schedule 的场景（moveSchedule 前查 oldSchedule）强制确认。

### P1-3 postpone 只改 deadline、不改 Schedule（违反核心规则）
`tasks/[id]/action/route.ts` 的 `postpone`：只 `data.deadline = d + days`，**已排期的 schedule 原封不动** → 任务还在原时间点执行，但截止日期推后了。项目铁律"改时间必须通过 Schedule Service"。且 `postponedCount`（专门建的腐化计数）**从未被更新**。修复：postpone 时同步 `moveSchedule` 到新日期，并 `postponedCount++`。

### P1-4 多任务可同时 in_progress（状态机缺陷）
`tasks/[id]/action` 的 `start` 不检查是否已有 in_progress 任务。Today 页面 `findFirst({ status: "in_progress" })` 取到哪个不确定 → 页面显示随机。修复：start 时原子地把其他 in_progress 任务置回 not_started（事务内）。

### P1-5 删除操作无事务（两处重复实现）
- `tasks/[id]/action` 的 `delete`：timeLog → schedules → children → task 四步
- `executor.ts` 的 `delete_task`：同样四步

中途失败 → 孤儿数据。应合并为一个 `$transaction`，且**两处逻辑重复**，应收敛到 `task/service.ts` 统一实现（DRY）。

### P1-6 executeReschedule 注释与实现不符
`decision/executor.ts:46-48` 注释说"Only delete today's AI schedule (preserve user/manual)"，实际调用 `deleteFutureSchedules` 删的是**该任务所有未来 schedule（不限 source）**，然后重建一条。用户手动排的重复任务安排会被清掉。修复：只删 `source: "ai"` 的未来 schedule，或按注释意图重写。

### P1-7 fetch 无超时（LLM 挂起即悬挂）
`client.ts` 两个调用 + `ai-config` POST 测试连接均无 AbortController。配置了一个黑洞 URL 或 LLM 服务端挂起 → API 路由永远挂着，浏览器转圈。修复：统一封装 `fetchWithTimeout(url, init, 30_000)`。

### P1-8 computeTrustScore 取样不保证"最近"
`decision-engine.ts:241` `take: 100` 无 `orderBy` → SQLite 返回顺序不保证，取到的可能不是最近 100 条，Trust Score 失真。加 `orderBy: { createdAt: "desc" }`。**同类问题**：pattern-mining Rule 2（take 30 无排序）、advanced.ts 的 4 个 take 查询均无排序。

### P1-9 verifyHypothesis 是"假验证"
`advanced.ts:147-153`：只要最近 7 天**存在任意** pattern 就认为假设验证通过 → LLM 幻觉假设直接写入长期记忆（confidence × 0.7）。这会让记忆库被污染。修复：做真实的关键词/指标比对，否则宁可不写。

### P1-10 runDailyAIPipeline 无分步容错
`advanced.ts:193-210`：`runPatternMining` 一旦抛错，lifecycle / resurrection / UserModel 全部不执行。每步独立 try-catch。

### P1-11 登录无限流
`auth.ts` Credentials 无失败计数/冷却。个人应用风险有限，但至少加简单的 IP + email 组合限速（如 5 次/分钟）。

### P1-12 TaskForm scheduled 类型缺 endTime 校验
`task-form.tsx`：选了 scheduled 但只填 startTime → 提交后 `POST /api/tasks` 因 `!endTime` **不创建 schedule**，任务类型却是 scheduled → 在 Plan 里"消失"（查不到也排不上）。修复：前端校验 endTime 必填；后端兜底（缺 endTime 时按 startTime + estimatedMinutes 或 1h 补）。

### P1-13 全天事件（scheduledEnd = null）被时间查询漏掉
`deleteFutureSchedules` / `replaceSchedule`（`schedule/service.ts:71,83`）用 `scheduledEnd: { gt: now }` —— SQL 中 `NULL > x` 为 NULL，**全天 schedule 永远删不掉**。AI 重排时全天任务会残留旧 schedule（且与 P1-6 叠加，重复任务越积越多）。修复：条件加 `OR: [{ scheduledEnd: { gt: now } }, { scheduledEnd: null }]`。

### P1-14 ai-config 安全与体验
- `PUT /api/ai-config`：baseUrl 不校验协议（任意 URL，SSRF 低危）；apiKey **明文落库**
- 体验：PUT 必须重发完整 apiKey（GET 只回掩码），建议"留空则不修改"
- 修复：zod 校验 `baseUrl` 必须 http(s) 且不允许 localhost/内网段（可配置）；apiKey 至少提示风险

### P1-15 WeekCalendar 任务块未排序、会重叠遮挡
`plan/page.tsx`：同一天多个任务按 absolute 定位，不按时间排序时后面的任务块盖住前面的；跨天任务（23:00–01:00）顶部溢出。修复：按 startTime 排序 + 溢出裁剪。

## 四、P2 — 工程化改进（长期）

1. **`any` 泛滥**：`plan/service.ts` 的 `deduplicate/toPlanItem(entries: any[])`、`agent/chat/route.ts` 的 `agentResponse: any`、`tasks/[id]/action` 的 `body: any`。全部换 Prisma 推断类型 + zod。
2. **重复逻辑未收敛**：schedule 去重逻辑在 `plan/service.ts`、`week-calendar/route.ts`、`task-execution-state.ts` 三处各写一遍；delete_task 两处；create_task 两处（executor + confirmed）。应抽 `task/service.ts`、`schedule/query.ts`。
3. **魔法字符串状态**：`"not_started"/"delayed"/"in_progress"` 等散落 50+ 处，无类型约束（SQLite 不支持 Prisma enum，但应导出 `TASK_STATUS` 常量集中引用）。
4. **错误处理规范**：API 路由 `catch {}` 全部吞掉返回裸 500，无日志、无 code。建议：统一 `{ success: false, error: { code, message } }` + 服务层业务异常 + `console.error` 至少留痕。
5. **可观测性为零**：全项目几乎没有 `console.error`（只有 planner 一处）。加 pino 或 consola 结构化日志。
6. **测试缺失**：`tests/` 仅 2 个文件。**优先给规则引擎补单测**：fallback parser（时区！）、today-decide 意图识别、pattern-mining 8 条规则、resolveMemoryConflicts。这些是零 AI 核心，回归风险最高。
7. **Schema 细节**：
   - `DecisionLog.reason` 与 `reasoning` 双字段冗余
   - `save_memory` typeMap 把 fact/event/lifecycle/project/goal 全映射成 temporary_context，语义丢失
   - 所有关联 User 的模型缺 `onDelete: Cascade`（删用户会 FK 报错）
8. **fetch 竞态**：前端页面无 AbortController，快速切换页面时旧请求 setState（React 18 下无害但浪费；建议加载时忽略过期响应）。
9. **today-decide 意图误判**："明天要交作业"（提示 deadline）会被判为 postpone；`findTask` 匹配失败时静默 fallback `tasks[0]`，可能对错任务出建议。
10. **extractCoreAction**：正则无 `g` 标志，`replace` 只清第一处时间词，标题会残留"下午3点"。

## 五、团队技术提升路线（为什么 + 怎么做）

### 1. 先立规矩：时区与日期（本周）
新增 `src/lib/date.ts` 统一出口 + lint 规则禁止裸 `toISOString().split("T")`（写个 eslint 自定义 rule 或在 code review checklist 里强制）。**这次时区 bug 的根本原因是每人各写各的日期逻辑**。

### 2. 分层架构收敛（2-4 周）
当前 API 路由直接写 prisma 的散乱查询与业务逻辑混在一起。目标分层：

```
Route（校验/鉴权/响应）→ Service（业务+事务）→ Repository（Prisma 查询）
         ↑ zod schema                      ↑ 业务异常
```

已做的 `schedule/service.ts`、`plan/service.ts` 是正确方向，把 `task` 的增删改、`inbox confirm`、`views` 查询也收敛进去。**验收标准：一个 prisma 调用不出现在 route 层。**

### 3. 事务纪律
写操作（尤其"先删后建"）一律 `$transaction`；多步业务（create+schedule、delete 四连）必须原子。在 PR review checklist 固化："任何两行以上写操作 = 事务"。

### 4. 类型安全 = 生产力
- `npm i -D zod` 已装：所有 POST body 过 zod，`z.infer` 导出类型，消灭 `body: any`
- Prisma 类型 `Prisma.TaskGetPayload<{ include: {...} }>` 替代手写 interface

### 5. 测试策略（重点：零 AI 核心）
| 模块 | 测试点 |
|---|---|
| `lib/date.ts` | 时区边界（0:00、20:00、UTC+8）|
| fallback parser | 相对日期、分类、时间段提取 |
| today-decide | 5 种意图 + 记忆增强 |
| pattern-mining | 8 条规则的阈值边界 |
| schedule service | 事务回滚、重复 schedule 清理 |

### 6. 可观测性（1 周）
每个 API 路由统一 try-catch 包装 + 请求日志（method/path/status/耗时/userId）。用 `pino` 或简单 wrapper 均可。

### 7. 前端交互验收标准
**"每个 button 必须有 onClick 或不存在"**。本轮审查最大的用户伤害不是 bug，是假按钮。上线前过一遍：全站点击无死区。

### 8. CI 固化（半天）
GitHub Actions：`pnpm lint && pnpm test && pnpm build` 三件套，PR 必过。防止回归。
