# 服务层 ↔ 数据层交互审计报告（2026-08-02 第七轮）

> 范围：业务服务（Schedule/Plan/Task/决策执行）与数据库交互的规则完整性
> 验证：tsc 零错误 / vitest 29/29 / build 成功

---

## 一、核心结论

**"Schedule 唯一时间源"规则此前被 5 处绕过**（edit-schedule 批量、PUT tasks、decision/executor 手写、batch_reschedule、tasks POST 事务内直写），状态机存在 completed/cancelled 复活漏洞，snoozeUntil 残留导致任务"消失"。本轮全部封堵，并让两条死链路（plan/analyze 健康分、dedup 规则）复活。

## 二、P0 修复（4 项）— 规则被绕过 / 状态机漏洞

| # | 问题 | 修复 |
|---|---|---|
| P0-1 | edit-schedule 的 future/all 分支**直接 update 排期时间绕过 service**，且 `scheduledEnd!` 对全天事件（null）直接 TypeError 崩溃 | 事务内 null 分叉处理（全天事件保持 null 平移） |
| P0-2 | **PUT /api/tasks/[id] 直写 Task.startTime/endTime**（产生第二个时间事实源）+ status 任意字符串直写（状态机完全旁路） | 白名单化：移除时间/状态直写；category 走归一化 |
| P0-3 | action `start` 对 completed 任务不拦截 → **完成任务"复活"**且 completedAt 残留，统计自相矛盾 | 拦截 completed/cancelled + 复活时清 completedAt/snoozeUntil |
| P0-4 | timer start/resume 对 cancelled/snoozed 不拦截（复活+带过期 snoozeUntil）+ 无互斥（可双 in_progress） | cancelled 拦截 + 全量互斥（与其他进行中任务互斥）+ 清 snoozeUntil |

## 三、P1 修复（7 项）

| # | 问题 | 修复 |
|---|---|---|
| P1-1 | **去重规则三处不一致**：plan/service（精确时间）、week-calendar（自然日）、exec-state（取最早）→ 同任务同日显示互不相同 | 抽 `deduplicateByDay` 统一（同任务+同自然日取最新），week-calendar 复用 |
| P1-2 | **plan/analyze 死链路**：健康分/冲突建议生成了但无任何前端消费 | Plan 页顶部新增「计划健康度」条（分数 + 首条警告） |
| P1-4 | apply-decision 不传 targetScheduleId → **重复任务拖拽折叠清空** | week-calendar 返回 scheduleId + 前端拖拽/弹窗透传 → moveSchedule(targetScheduleId) |
| P1-5 | decision postpone 与 /action postpone 语义分叉（不清 snoozeUntil） | 对齐：snoozed 延期必解冻 |
| P1-6 | decision skip 绕过 service 且无事务 | 改走 deleteFutureSchedules |
| P1-10 | **snoozeUntil 残留**：complete/cancel/delay/pause 均不清，暂缓语义丢失 | 所有离开 snoozed 的转移统一清 |
| P1-11 | **snoozed 永不解冻**：过期暂缓任务永远"消失"（无自动迁移） | daily-cron 每日解冻过期暂缓任务 |

## 五、遗留（已标注，未做）

1. **死路由群**：/api/plan/{analyze 已活, week, day, move, repeat, edit-schedule, delete-schedule, task/[id]}、/api/schedule、/api/views/week、/api/tasks/[id]/{timer, exec-state}、/api/decision/*、/api/ai/{plan,today-decide,today-suggest,ingest,parse} 无前端消费方——其中含 service 旁路代码（edit-schedule 已修，其余未修）。建议后续"接线或删除"
2. planner saveSchedule 逐条 N+1 + 无整体事务（批量排期时）——中等改动，下轮做
3. Schedule Service 不支持 tx 注入 → 事务内无法复用 service（旁路根因）——架构级改造
4. Task.startTime/endTime 字段为死字段（只剩 views/week 读取，该路由也无人消费）——建议删字段
5. apply-decision 多 change 非原子（逐条事务）

## 六、审计方法论沉淀

- **时间源唯一性**：grep 所有 `prisma.schedule` 写操作 vs service 出口 → 找出旁路
- **状态机合法性**：枚举所有 status 写入点，检查流转合法性 + 附属字段（completedAt/snoozeUntil）一致性
- **消费链**：对每个"生成结果"的 API 反向 grep 前端 fetch → 找出死链路
